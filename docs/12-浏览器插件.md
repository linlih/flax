# 12 浏览器插件：一键把论文存进 Flax

> 状态：v0.5（2026-11-19），第 1 阶段做完了（第 8 节）。v0.2 读了 Zotero 两个仓库的源码，改了第 3 节，去掉了配对令牌；v0.3 加了第 0 阶段的实测结果；v0.4 定了端口、打包框架、权限和窗口行为，设计上没有待决定的事了；v0.5 第 1 阶段做完，记了实际做法和设计不一样的地方。路线图里在阶段 3（[06](06-路线图.md)「浏览器插件：一键保存论文」）。

## 1. 要做成什么样

在浏览器里看到一篇论文（arXiv、期刊页面、OpenReview、直接打开的 PDF），点工具栏上的 Flax 图标，论文就进了桌面端的文献库：元数据是对的，PDF 也在。

- **一下就好**：点图标就开始存，弹出的小窗只显示进度和结果，不用填表。想放进哪个文件夹、打什么标签，在小窗里可以顺手改，不改也行。
- **已经存过的要看得出来**：打开一篇库里已有的论文，图标上有个小勾，点开显示「已在文献库」和「在 Flax 中打开」。
- **付费墙后面的也能存**：用户在学校网络或登录了出版商账号时，浏览器能下载 PDF，Flax 自己去下载就会被挡。所以 PDF 由插件在浏览器里下，再交给桌面端（Zotero 也是这么做的，见第 3 节）。
- **桌面端没开**：提示「Flax 没有打开」并给一个「打开 Flax」按钮，打开后自动接着存。
- **本地优先**：插件只和本机的 Flax 说话，不经过任何服务器。

不做：网页快照（存整个网页）、插件里看论文、插件里的笔记和批注、手机浏览器。

## 2. 总体结构

```
浏览器                                                   桌面端（Electron 主进程）
┌──────────────────────────────────────────┐            ┌─────────────────────────────────┐
│ 内容脚本（每个页面）                       │            │ connector.ts                    │
│  读 citation_* meta、arXiv 编号、DOI、     │            │  只监听 127.0.0.1:<端口>        │
│  PDF 链接 → 交给后台                       │            │  校验 Host、自定义头、Origin     │
├──────────────────────────────────────────┤  HTTP/JSON │                                 │
│ 后台（MV3 service worker）                 │ ─────────→ │  /ping /lookup /save /file       │
│  找桌面端、存论文、下载 PDF（带 cookie）   │            │         │                       │
│  （带用户的 cookie）、图标上的小勾          │ ←───────── │         ▼                       │
├──────────────────────────────────────────┤            │ Importer（@flax/core）           │
│ 小窗（popup）                              │            │  addFromText / importBytes       │
│  进度、结果、文件夹和标签、打开 Flax        │            │  查元数据、下载 arXiv PDF、查重   │
└──────────────────────────────────────────┘            └─────────────────────────────────┘
          桌面端没开时：flax://save?... 唤起应用，然后重试
```

桌面端这边几乎都是现成的：粘贴 DOI 或 arXiv 链接建记录（`Importer.addFromText`）、联网查元数据、arXiv 自动下 PDF、按哈希查重，都已经有了。要新加的只是「一个让插件能连上的入口」和「从内存里的 PDF 导入」。

## 3. 调研：别人怎么做

### Zotero Connector（最成熟的参考）

2026-11-19 读了两个仓库的主分支源码：桌面端 [zotero/zotero](https://github.com/zotero/zotero) 的 `chrome/content/zotero/xpcom/server/`（`server.js`、`server_connector.js`），插件 [zotero/zotero-connectors](https://github.com/zotero/zotero-connectors) 的 `src/common/connector.js`、`itemSaver_background.js`、`src/browserExt/`（`manifest-v3.json`、`background.js`、`offscreen/`）。下面的结论都来自源码，个别地方注明了是从论坛看来的。

**桌面端的本地服务**

- 只监听 127.0.0.1，端口默认 **23119**（设置项 `httpServer.port`，可以改），没有自动换端口。
- 接口有二十来个，和我们相关的：
  - `ping`：GET 只回一句「Zotero is running」；POST 回一组设置（比如支不支持上传附件），顺便检查插件版本，版本太旧时桌面端弹提示，不兼容时返回 412。
  - `saveItems`：存插件识别好的条目，请求里带一个插件生成的 `sessionID`。
  - `saveAttachment`：给同一个 session 里刚存的条目挂 PDF。**请求体就是 PDF 的字节**，元数据（`parentItemID`、`title`、`url`）放在 `X-Metadata` 请求头里，URL 参数带 `sessionID`。
  - `saveStandaloneAttachment`：直接打开的 PDF，没有元数据，存完桌面端自动识别（`RecognizeDocument.autoRecognizeItems`）。
  - `getSelectedCollection`：返回桌面端当前选中的文件夹，以及所有能写的文件夹和标签，给插件的小窗用。
  - `updateSession`：存完以后改 session 里条目的位置（`target`）、标签（`tags`）、附加笔记（`note`）。
- **防网页乱调用，靠的是请求头和 CORS，没有令牌**（`server.js` 的 `_processEndpoint`）：
  1. `Host` 头必须是 `127.0.0.1`、`[::1]` 或 `localhost`，防 DNS 重绑定。
  2. 判断是不是浏览器发来的：UA 以 `Mozilla/` 开头，或者带了 `Origin`。是浏览器的话，**必须带 `X-Zotero-Connector-API-Version` 或 `Zotero-Allowed-Request` 头**，否则直接断开连接。网页要带这种自定义头就得先过 CORS 预检，而桌面端只给 Zotero 自己的书签工具（bookmarklet）回 `Access-Control-Allow-Origin`，所以网页过不了预检。插件有 `host_permissions`，不受 CORS 限制，能直接带上。
  3. 唯一的例外是用户在地址栏直接打开 `/connector/ping`（`Sec-Fetch-Mode: navigate`），方便用户自己检查 Zotero 开没开。
  4. 每个接口声明自己收哪些方法、哪些 `Content-Type`，不符合就 400。
  - **本机别的程序能随便调**，Zotero 不防这个。
- 每个响应都带 `X-Zotero-Version`。插件靠它分辨「是 Zotero 回的错误」还是「这个端口上是别的程序」：没有这个头的 4xx 一律当作 Zotero 没开。

**插件**

- MV3，一套代码出 Chrome、Edge、Firefox，Safari 单独包一层。权限要得很全：`host_permissions` 是 `http://127.0.0.1/*` 加上所有 http、https 网站，`permissions` 有 `cookies`、`webRequest`、`declarativeNetRequest`、`scripting`、`offscreen`、`tabs` 等。论坛上有人希望改成「点击时才允许访问」，现在不支持。
- **PDF 在插件的后台下载**（`_fetchAttachment`），用的是浏览器的登录状态：
  - 用 `arraybuffer` 下载，带上 `Referer`；
  - **手动把 cookie 拼进请求头**：Chrome 后台发请求时会忽略带 `partitionKey` 的 cookie，而 Cloudflare 的通行 cookie 正好是这种（Chromium issue 458071621）；Firefox 开了第一方隔离时也不会自动带 cookie。所以要 `cookies` 权限；
  - 检查返回的 `Content-Type` 是不是想要的类型，不是就算失败；
  - 被 Cloudflare 一类的人机验证挡住时，先在隐藏 iframe 里过一遍 JS 检测，不行就弹一个窗口让用户自己过验证，再重下（`botBypass.js`、`browserAttachmentMonitor/`，只对白名单里的网站这么做）。
- **识别网页靠 translator 脚本**（每个网站一个，几百个）：代码先从桌面端的 `getTranslatorCode` 拿，桌面端没开时从 `repo.zotero.org` 拿；在一个沙盒页面里执行。MV3 的 service worker 里不能执行拿来的代码，所以这个沙盒页面放在 offscreen 文档里——**offscreen 是给 translator 用的，不是用来下载 PDF 的**。这些脚本是 AGPL-3.0，和 Flax 的许可证兼容，以后真要覆盖大量出版商网站可以考虑借用，但第一版不需要（见第 5 节）。
- 直接打开的 PDF 标签页：后台看响应头的 `Content-Type: application/pdf`，换一个 PDF 图标，点了走 `saveStandaloneAttachment`。
- **Zotero 没开时**：弹窗，三个按钮——重试、取消、「存到 zotero.org 的在线文献库」；附带下载链接和排查说明。**它不会去唤起桌面端**。我们没有在线文献库，所以第 4.5 节的 `flax://` 唤起是我们自己的设计，不是照搬。
- Safari 例外：要用户单独授权访问 `127.0.0.1`。插件会先解释为什么要这个权限，再触发 Safari 的授权框；被拒绝时引导用户去 Safari 设置里打开。

### 插件和本机程序通信的三种办法

| 办法 | 怎么做 | 好处 | 问题 |
|---|---|---|---|
| **本地 HTTP 服务**（Zotero、各种下载器） | 桌面端监听 127.0.0.1 的端口，插件 `fetch` | 简单，所有浏览器都一样；能传大文件；双向 | 端口可能被占；要自己防网页和 DNS 重绑定；Chrome 新的本地网络权限（下面） |
| Native Messaging | 在每个浏览器的指定目录装一个清单文件，浏览器拉起一个本机程序，用标准输入输出传 JSON | 浏览器官方通道，网页碰不到，没有端口问题 | 每个浏览器的清单位置不同（Chrome、Edge、Firefox、Arc……），安装时都要写；单条消息有大小上限，传 PDF 要分片；拉起的是新进程，还得再转给正在运行的 Flax |
| 自定义协议 `flax://` | 插件打开 `flax://save?url=…` | 桌面端没开时能把它唤起 | 只能单向传一小段文字，传不了 PDF，也拿不到结果；每次可能弹「要打开 Flax 吗」 |

**结论**：主通道用本地 HTTP 服务；`flax://` 只用来在桌面端没开时把它唤起。Native Messaging 不做（第 0 阶段实测插件能直接连，见下）。

### Chrome 的本地网络访问（Local Network Access）

Chrome 142 开始，**网页**访问本机和局域网地址要用户授权，Service Worker 自己没法弹授权框，必须是之前授权过的来源（[Chrome 官方说明](https://developer.chrome.com/blog/local-network-access)）。官方文档没提插件。

Zotero 碰到过这个问题（[论坛帖](https://forums.zotero.org/discussion/125333/sharing-my-fix-for-the-zotero-connector-connection-issue)）：2025 年 7 月，Chrome Dev 140 上 Zotero 插件连不上桌面端，要在插件的「本地网络访问」权限里手动改成「允许」。Zotero 开发者认为这个限制本来就不该管插件，向 Chromium 报了 bug；8 月回复说 Chrome 已经修了，「以后的 Chrome 版本不会再有这个问题」。Zotero 的插件代码里也没有任何针对 Chrome 本地网络权限的处理，只处理了 Safari。

### 第 0 阶段实测（2026-11-19）

在 Chrome 157.0.8103.79、Edge 157.0.4341.60（macOS）上测过：两个浏览器都用全新的临时用户目录，桌面端换成一个按第 4.2 节规则写的最小服务，插件只做了连接测试。Firefox 本机没装，Safari 不在第一版范围，都没测。

| 谁发的请求 | Chrome 157 | Edge 157 |
|---|---|---|
| 插件 service worker，有 `http://127.0.0.1/*` 主机权限，带 `X-Flax-Connector` | **200**，没有弹授权框 | **200** |
| 插件页面（小窗也算这种），同上 | **200** | **200** |
| 同一个插件，不带自定义头 | 服务端断开连接（`reject:no-header`） | 同左 |
| 插件**没有**主机权限 | 浏览器先发 CORS 预检，服务端不放行，请求失败 | 同左 |
| 公网网页（https://example.com），没给本地网络授权 | **请求根本没到服务端**，一直卡到超时（在等授权） | 请求到了服务端：带头的被预检挡住，不带头的「简单请求」被 `reject:no-header` 断开 |
| 公网网页，已经给了本地网络授权 | 请求到了服务端，结果和右边 Edge 一样被挡住 | 同左 |

结论：

- **插件连本机没有问题**，Chrome 的本地网络访问管不到有主机权限的插件，和 Zotero 开发者说的一致。主通道用 HTTP 就够了，**不需要 Native Messaging**。
- **`host_permissions` 里必须有 `http://127.0.0.1/*`**，没有就会被 CORS 挡住（预检过不了）。
- **不能指望浏览器替我们挡网页**：Edge 157 没有拦公网网页访问本机，Chrome 用户点了「允许」以后也不拦。真正起作用的是服务端的规则——「浏览器发来的请求必须带自定义头」和「不回 `Access-Control-Allow-Origin`」，两个浏览器上都挡住了网页。
- 没测企业管理的电脑（可能有策略禁止访问本机）；插件是开发者模式加载的，商店安装的权限模型一样，应该没有区别。

顺便发现：Chrome 137 起，正式版 Chrome 不认 `--load-extension` 启动参数，加 `--disable-features=DisableLoadExtensionCommandLineSwitch` 也不行（157 上实测）。以后要自动测试插件，用 `--remote-debugging-pipe --enable-unsafe-extension-debugging` 启动浏览器，再调 CDP 的 `Extensions.loadUnpacked`，这次就是这么跑的。

## 4. 桌面端：本地连接服务

新文件 `apps/desktop/src/main/connector.ts`，用 `node:http`，在 `setup()` 里和 `Importer` 一起建。

### 4.1 监听

- 只绑 `127.0.0.1`，不绑 `0.0.0.0`。
- **固定端口 `27183`**，和 Zotero 一样不自动换（2026-11-19 定）。查过：本机和 `/etc/services` 里没有占用，网上也查不到常见软件在用。
- 端口被占时，桌面端在设置里显示「端口 27183 被别的程序占用」，让用户换一个；插件的选项页里也有同一个端口设置，两边要改成一样的。插件只连这一个端口，不挨个试。
- 设置里加一个开关「允许浏览器插件连接」，默认开。

### 4.2 防止网页乱调

本地端口谁都能连，要防的是**用户打开的恶意网页**借浏览器调我们的接口（往库里塞东西、读出库里有什么）。本机别的程序不在防的范围内：能在用户账号下跑程序的，也能直接读 SQLite。

照 Zotero 的做法（第 3 节，已经被大量用户验证过），再加一条 Origin 检查：

1. **Host 头**必须是 `127.0.0.1`、`[::1]` 或 `localhost`（带端口）——挡 DNS 重绑定（恶意域名解析成 127.0.0.1）。
2. **必须带自定义头 `X-Flax-Connector: <接口版本>`**，否则直接断开。网页要带自定义头就得先过 CORS 预检，而我们**不对任何来源回 `Access-Control-Allow-Origin`**，网页过不了；插件有主机权限，不受 CORS 管。
3. **有 `Origin` 头的话，必须是 `chrome-extension://`、`moz-extension://` 或 `safari-web-extension://` 开头**。Zotero 没做这一条，我们加上，多一层保险（就算哪天某个浏览器的预检规则有漏洞，网页的 Origin 也冒充不了插件）。
4. 每个接口只收声明过的方法和 `Content-Type`（`application/json`、`application/pdf`），否则 400；请求体限制大小（PDF 200 MB，JSON 1 MB），超时 2 分钟。
5. 唯一的例外：`GET /ping` 是用户在地址栏打开的（`Sec-Fetch-Mode: navigate`），就回一句「Flax 正在运行」，方便排查。
6. 每个响应都带 `X-Flax-Version`。插件没看到这个头就当作 Flax 没开（端口上可能是别的程序）。

**第一版不做配对令牌**。最早的草案里有（桌面端弹框确认、发令牌），但 Zotero 这么多年没有令牌也没出问题，上面几条已经挡住了网页。令牌只多防了「本机别的程序」，而那不是要防的场景。以后要是加「局域网里的另一台电脑也能存」，再加配对。

### 4.3 接口

| 接口 | 用途 | 请求 | 返回 |
|---|---|---|---|
| `POST /ping` | 插件找桌面端、看版本 | — | `{ app: "flax", version, apiVersion }`；插件太旧返回 412 |
| `POST /lookup` | 图标上的小勾：库里有没有 | `{ doi?, arxiv?, url? }` | `{ paperId, title, hasPdf } \| null` |
| `POST /save` | 存论文（元数据） | 见下 | `{ paperId, status: "added" \| "existing", needsPdf }` |
| `POST /file?paperId=…` | 把浏览器下好的 PDF 挂上去（同 Zotero 的 `saveAttachment`：字节放请求体，元数据放请求头） | 请求体是 PDF 字节，`Content-Type: application/pdf`，`X-Flax-Meta: {"url","fileName"}` | `{ status: "attached" \| "same_file" \| "not_pdf" }` |
| `POST /file`（不带 paperId） | 直接打开的 PDF，没有元数据 | 同上 | 走现有的 PDF 导入流程（读 PDF 里的 DOI、查元数据、认不出来问要不要让 AI 识别） |
| `GET /targets` | 小窗里选文件夹和标签 | — | `{ folders, tags, current }` |
| `POST /update` | 存完以后改文件夹、标签 | `{ paperId, folderId?, tags? }` | `{ ok }` |
| `POST /open` | 「在 Flax 中打开」 | `{ paperId }` | 窗口拉到前面并打开这篇 |

`/save` 的请求体：

```jsonc
{
  "url": "https://arxiv.org/abs/2401.00001",
  "ids": { "doi": "10.1145/…", "arxiv": "2401.00001" },   // 内容脚本找到的
  "meta": {                                                 // 网页上的 citation_* 信息，作为兜底
    "title": "…", "authors": ["…"], "year": 2024, "venue": "…", "abstract": "…"
  },
  "pdfUrl": "https://…/paper.pdf",                          // 网页上能找到的 PDF 链接
  "folderId": null, "tags": []
}
```

### 4.4 接到现有的导入流程

- 有 DOI 或 arXiv 编号：走 `Importer.addFromText` 的同一套逻辑（建记录 → 查 Crossref、arXiv → arXiv 的自动下 PDF）。需要把它拆一下，接受已经解析好的 `ids` 和网页上的 `meta`（查不到元数据时用网页的标题、作者兜底，不要只剩一个编号当标题），并返回 `paperId`。
- 已经在库里：返回 `existing`，库里那条没有 PDF 的话返回 `needsPdf: true`，插件接着传 PDF。
- 没有编号（比如只有标题的会议页面）：用网页的 `meta` 直接建记录，标「需要确认」（`needsMatch`），和现在导入认不出的 PDF 一样走候选匹配。
- **`/file` 需要 `Importer` 新增「从内存导入」**：现在 `importOne(path)` 第一步就是按路径读文件，把它拆成 `importPaths → read → importData(data, fileName)`，`/file` 直接调 `importData`；带 `paperId` 时调一个新的 `attachData(paperId, data)`，逻辑和现有的 `relink`、`attached` 提示一样（哈希查重、确认是 PDF、`storeFile`、`addFile`）。这部分放在 `@flax/core`，补单元测试。
- 导入完照常发 `library:changed` 和提示，桌面端界面上能看到新论文进来。
- **窗口不跳到前面**（2026-11-19 定），只发一条系统通知「已存进文献库：<标题>」，点通知再打开这篇。想马上看就点插件小窗里的「在 Flax 中打开」（`/open`）。连着存几篇时，通知合并成一条。

### 4.5 桌面端没开

- 注册 `flax://` 协议（`app.setAsDefaultProtocolClient('flax')`，macOS 在 `Info.plist` 里声明，Windows 由安装包写注册表）。现在 `flax://` 只是内部给渲染进程读文件用的协议，**还没注册成系统协议**，需要新加。
- 同时要加 `app.requestSingleInstanceLock()`：Windows 上点 `flax://` 链接会再启动一个 Flax，得把参数交给已经开着的那个（`second-instance` 事件）；macOS 用 `open-url` 事件。
- 插件 ping 不到时，小窗显示「Flax 没有打开」和按钮；点按钮打开 `flax://open`，之后每秒 ping 一次，最多 15 秒，连上就接着存。
- 唤起时只传 `flax://open`，**不把论文信息放进链接**（链接会进系统日志和浏览器历史），等连上以后再通过 HTTP 传。

## 5. 插件端

### 5.1 识别页面

第一版不搬 Zotero 的 translator，只用通用规则，已经能覆盖绝大多数学术网站：

1. **`<meta name="citation_*">`**（Google Scholar 要求出版商加的那套：`citation_title`、`citation_author`、`citation_doi`、`citation_pdf_url`、`citation_arxiv_id`、`citation_publication_date`、`citation_journal_title`、`citation_conference_title`）。Springer、Elsevier、IEEE、ACM、Nature、ACL Anthology、OpenReview、PMLR、NeurIPS 论文页都有。
2. 其次 `<meta name="dc.identifier">`、`prism.doi`、JSON-LD 里的 `ScholarlyArticle`。
3. **网址规则**：`arxiv.org/abs|pdf|html/<编号>`、`doi.org/<DOI>`、`openreview.net/forum?id=`、`aclanthology.org/<编号>`、`semanticscholar.org/paper/…`。
4. 当前标签页直接是 PDF（`Content-Type` 或网址以 `.pdf` 结尾）：不找元数据，下载 PDF 走 `/file`，交给桌面端从 PDF 里认。
5. 都没有：图标灰掉，小窗说「这个页面上没找到论文」，并提供「把选中的 DOI / arXiv 链接存进来」（复用桌面端的 `idsInText`）。

编号格式由桌面端按粘贴文字的规则（`@flax/core` 的 `idsInText`）再认一遍，插件只管把网页上读到的原样送过去。所以插件不引用 `@flax/core`，包更小，识别规则也只有一份（第 1 阶段实际这么做的，最早的草案是想在插件里引用 core）。

### 5.2 存的流程

```
点图标
 ├─ ping 不到 → 「Flax 没有打开」[打开 Flax] [重试]
 └─ POST /save
      ├─ added / existing 且有 PDF → 完成 ✓
      └─ needsPdf 且网页上有 pdfUrl
           └─ 插件后台下载 pdfUrl（带 cookie 和 Referer）→ 是 PDF → POST /file?paperId
                ├─ 成功 → 完成 ✓
                └─ 下不到（登录页、HTML）→ 完成，提示「PDF 没下载到，可以之后在 Flax 里拖进来」
```

- arXiv 的论文桌面端会自己下 PDF，插件就不用再传了（`needsPdf` 会是 false），省一次传输。
- 下载 PDF 照 Zotero 的做法（第 3 节）：
  - 带上 `Referer`；用 `cookies` 权限读出这个网址的 cookie，**手动拼进请求头**——Chrome 后台发请求时不带分区 cookie（Cloudflare 的通行 cookie 就是这种），Firefox 开了第一方隔离时也不带；
  - 先看 `Content-Type`，再看前几个字节是不是 `%PDF`——出版商常常对未登录用户返回一个 HTML 登录页；
  - 被 Cloudflare 一类的人机验证挡住时，第一版不做 Zotero 那套绕过，直接提示「PDF 没下载到，打开 PDF 页面后再点一次」（那时当前标签页就是 PDF，走 `/file`）。
- 权限（2026-11-19 定）：**安装时就要所有网站**，和 Zotero 一样。`host_permissions` 写 `http://127.0.0.1/*`、`http://*/*`、`https://*/*`，`permissions` 要 `cookies`、`storage`、`scripting`、`tabs`。下载 PDF 需要对应网站的主机权限和 `cookies` 权限，PDF 又常常在另一个域名上，按需请求的话每个新网站都要点「允许」，体验不好。商店页面和首次安装的欢迎页里说清楚这些权限用来做什么：只在你点保存时读当前页面、下载 PDF，不收集浏览记录。

### 5.3 小窗

和桌面端同一套视觉（[DESIGN.md](../DESIGN.md)：托盘 + 白卡，单一蓝色强调色），宽 340 左右：

- 上：论文标题、作者、年份（来自网页，存完换成桌面端查到的）；
- 中：状态一行——「正在存…」「已存进文献库」「已在文献库」「PDF 没下载到」；
- 下：文件夹、标签（来自 `/targets`，改了马上 `/update`），「在 Flax 中打开」。

### 5.4 技术选型

- Manifest V3，TypeScript + React（和桌面端一致），一套代码出 Chrome、Edge、Firefox。
- 打包用 **WXT**（2026-11-19 定）：专门做跨浏览器 MV3 的框架，开发时热更新，按浏览器生成各自的 manifest。当时的版本是 0.21.5（2026-10-26 还在更新），只有一个维护者、还没到 1.0，所以锁定确切版本号，升级前看更新说明。万一以后不维护了，它底下就是 Vite，迁出来成本不高。
- 放在 `apps/extension/`，进 workspace，`@flax/core` 只引纯函数。
- Safari 要用 Xcode 包一层 macOS 应用，分发要 Apple 开发者账号——和 iOS 一样先不做（见 README 决策记录 2026-11-12）。

### 5.5 发布

- Chrome 网上应用店（一次性 5 美元开发者注册）、Edge 加载项（免费）、Firefox AMO（免费，要签名）。
- 国内用户进不去 Chrome 应用店的情况不少：GitHub Release 里同时放打包好的 zip，说明怎么在「开发者模式」里加载。
- 版本号和桌面端分开（插件和桌面端靠 `apiVersion` 对接，不要求一起升级）。

## 9. 直接打开的 PDF（2026-11-22）

第 1 阶段遇到直接打开的 PDF 标签页只提示「下一版才能存」：Chrome 的 PDF 查看器里读不到 citation_* 信息，网址里也常常没有编号，插件不知道这是哪篇。但桌面端本来就能「粘贴 PDF 链接添加」，所以不等第 2 阶段，先让 Flax 自己下载：

- 插件：PDF 标签页（`document.contentType` 是 `application/pdf`，读不到页面时看网址是不是 `.pdf`）也算论文，`/save` 带上 `isPdf: true`，等待时间放宽到 115 秒，小窗显示「Flax 正在下载这个 PDF…」。
- 桌面端：`addFromPage` 看到 `isPdf` 就按网址下载，走和拖进文件一样的导入（按文件哈希查重、读 PDF 里的编号联网查详情、认不出来问要不要让 AI 识别）。arXiv 的 PDF 例外，仍按编号存，详情更全。下载失败（404、要登录、下到的不是 PDF）把原因返回给插件，小窗里显示。
- 和第 2 阶段的区别：Flax 自己下载拿不到浏览器里的登录状态，学校账号才能下的出版社 PDF 还是存不了，会提示「要登录才能下载」。那部分仍由第 2 阶段的插件下载解决。
- 已知不足：通用 PDF 网址里没有编号，后台查不出库里有没有，图标上不会提前打勾；再点一次会重新下载，按文件哈希认出是同一篇，显示「已在文献库」。

验证：单元测试 3 个（下载存入和再存一次、下载失败的三种原因、arXiv PDF 仍按编号存），全部 344 个测试通过。端到端（Chrome 157 + 开发版 Flax 用临时资料文件夹）：

## 10. 网页里的保存窗口和 PDF（2026-11-22）

用户反馈「和 Zotero 比保存体验差很多」。读了 Zotero 插件的源码（`src/browserExt/background.js`、`src/common/inject/progressWindow_inject.js`、`src/common/ui/ProgressWindow.jsx`、`src/common/itemSaver*.js`），差别主要在点了以后：

| | Zotero | Flax 改之前 | Flax 现在 |
|---|---|---|---|
| 点图标 | 没有弹出小窗，直接存；网页右上角出现保存窗口（插进页面的 iframe），点别处不会消失，存在后台进行 | 浏览器小窗，点别处就关了，存也跟着断了 | 同 Zotero：后台存，网页右上角的窗口（shadow root 里，放进浏览器顶层 popover，网页的遮罩盖不住） |
| 文件夹、标签 | 窗口里「存到 [文件夹 ▾]」，默认桌面端选中的文件夹，存完还能改；标签、笔记 | 没有 | 「存到 [文件夹 ▾]」，默认上次选的（新存的一篇才自动放进去，已在库里的不动）；标签回车添加，可以从已有标签里选 |
| PDF | 插件带 cookie 下载，进度显示在窗口里；网页上没有时桌面端找开放获取的版本 | 只有 arXiv 和直接打开的 PDF | 插件带 cookie 下网页上的 `citation_pdf_url`，传给 Flax；下不到时 Flax 找 arXiv、OpenAlex 记录的开放获取 PDF；窗口里一行显示进度和原因 |
| 窗口什么时候关 | 存完 3 秒；鼠标离开后 2.5 秒；出错 8 秒；鼠标在上面、正在输入时不关 | — | 同 Zotero；没找到论文 4 秒；Flax 没开时不关，有「打开 Flax」「重试」 |
| 放不下窗口的页面 | 图标变成转圈、打勾 | — | 图标上显示「…」「✓」「!」，Flax 照常发系统通知 |

**接口**（接口版本升到 2，旧插件照样能用）：

- `POST /file?paperId=&name=&quiet=`：请求体是 PDF 本身（`Content-Type: application/pdf`，最大 200 MB），和 Zotero 的 `saveAttachment` 一样参数放在网址里。带 `paperId` 是配给刚存的那篇（已经有 PDF 的不换），不带是直接打开的 PDF 标签页，当作新的一篇导入。
- `POST /findPdf {paperId}`：Flax 自己找 PDF，等下完再回。arXiv 的从 arXiv 下；有 DOI 的问 OpenAlex（`/works/doi:…` 的 `best_oa_location` 和开放获取的 `locations`），最多试 3 个地址。不带用户的邮箱（OpenAlex 的「礼貌池」要邮箱，不用也能查）。
- `POST /targets`：文件夹（按树的顺序，带层级）和已有标签。
- `POST /update {paperId, patch: {addFolder, removeFolder, addTags, removeTags}}`：窗口里改了文件夹、标签。不认识的文件夹忽略。
- `/save`、`/lookup` 的结果多了 `pdf: 'yes' | 'downloading' | 'no'`，插件据此决定还要不要下 PDF。`/save` 带 `quiet: true` 时 Flax 不发系统通知（窗口已经告诉用户了）。

**和 Zotero 不一样的地方**

- 默认文件夹是「上次选的」，不是「Flax 里当前选中的」：Flax 的选中状态在界面里，连接服务拿不到；Zotero 也有一个「最近用过」的列表。
- 不做附加笔记、网页快照、按网站的识别脚本，以后再说。
- PDF 下载只靠浏览器自动带的 cookie。Zotero 额外用 `cookies` 权限把带 `partitionKey` 的 cookie（Cloudflare 的通行 cookie 是这种）手动拼进请求头，还会用隐藏 iframe 或弹窗过人机验证；这两样都没做，遇到这种网站会显示「网站给的不是 PDF（可能要登录，或者要先过人机验证）」。也没带 `Referer`。

**验证**

- 单元测试：桌面端 `/file`、`/targets`、`/update`、`/findPdf` 和 PDF 配给、OpenAlex、文件夹和标签共 7 个；全部 351 个测试通过，`npm run typecheck` 通过。
- 端到端（Chrome 157 + 开发版 Flax 用临时资料文件夹；用 `chrome.action.onClicked.dispatch` 模拟点图标，CDP 读 closed shadow root 里的文字、截图）：

| 页面 | 窗口里的过程 | 库里的结果 |
|---|---|---|
| arxiv.org/abs/1706.03762，打一个标签 | 正在存 → 已存进文献库 · Flax 正在找免费的版本 → PDF 已存好 | PDF 有，标签有；输入框有焦点时窗口不收 |
| aclanthology.org/2020.acl-main.703/ | 已存进文献库 · 正在从网页下载 → PDF 已存好，3 秒后收起 | PDF 是网页上的那个 |
