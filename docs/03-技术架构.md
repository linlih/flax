# 03 技术架构

> 状态：草案 v0.1（2026-11-03）。

## 1. 总体结构

```
┌───────────────────── 共享 TypeScript 核心（packages/core）─────────────────────┐
│ 数据模型 · 存储抽象 · CRDT 同步 · 元数据抓取 · 检索（全文 + 向量） · AI · 翻译 │
└───────────────────────────────────────────────────────────────────────────────┘
          │                                              │
  桌面端：Electron + React                       移动端：React Native
  ├─ 文献库、笔记、AI 界面：React                 ├─ 文献库、笔记、AI 界面：RN
  ├─ 阅读器：PDF.js（或 MuPDF）+ 批注叠加层        ├─ iPad 阅读器：原生 Swift 模块
  └─ 重任务：Node worker / Rust 原生模块            │    （PDFKit + PencilKit）
     （PDF 解析、索引、文件哈希）                 └─ Android 阅读器（后期）：PDFium + 手写笔事件
          │                                              │
          └──────────────── 同步层 ──────────────────────┘
               元数据 / 批注 / 笔记：CRDT 增量同步
               PDF 文件：按内容哈希存到用户自选的存储
```

## 2. 技术选型与理由

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | TypeScript（主力）+ Swift（iPad 阅读器）+ Rust（可选的性能模块） | 桌面和移动端可以共享核心逻辑 |
| 桌面 | **Electron** | 各平台统一用 Chromium，渲染一致，最好打磨；PDF.js 表现最好。Tauri 在不同平台用不同的系统 WebView，打磨成本高 |
| 移动 | **React Native** | 和 Electron 一样跑 JavaScript，可以复用核心包；关键界面可以用原生组件 |
| iPad 阅读器 | **原生 Swift：PDFKit + PencilKit** | Pencil 的低延迟、压感、防误触只有原生能做好。这是必须项 |
| 桌面 UI | React + 自建设计系统 | 体验是护城河，组件要自己掌控 |
| 本地数据库 | SQLite（FTS5 全文检索 + sqlite-vec 向量检索） | 单文件、可靠、离线可用 |
| 同步 | 按记录、按字段合并的变更日志（2026-11-09 改，不用 Automerge 或 Yjs，见 [11](11-移动端与同步规划.md)） | 多设备自动合并，不用手动解决冲突；笔记是普通 .md 文件，按行三方合并 |
| 文件存储 | 用户自选：本地文件夹、iCloud Drive、WebDAV、S3、R2 | 不卖存储空间，用户成本接近零 |
| AI | 统一的模型接口：用户自带 Key（各大模型厂商）+ 本地模型（Ollama） | 不被单一厂商锁定，可以离线使用 |

### 被放弃的方案
- **Tauri 2**：桌面和移动端一套代码很诱人，但系统 WebView 的差异（尤其 Linux）和移动端的不成熟，会和"打磨体验"的目标冲突。
- **Capacitor 或网页方案做 iPad**：在 WebView 里用 Pencil 手写，延迟明显，不能满足必须项。
- **Flutter**：PDF 的文本选择、高亮、批注生态弱。
- **全原生（每个平台单独写）**：体验最好，但小团队做不下来。

## 3. 代码仓库结构（monorepo，建议）

```
apps/
  desktop/          # Electron 应用
  mobile/           # React Native 应用（iPad 优先，手机其次）
    ios/Reader/     # 原生 Swift 阅读器模块（PDFKit + PencilKit）
packages/
  core/             # 数据模型、业务逻辑，不依赖任何平台 API
  storage/          # 存储抽象：SQLite 适配器（better-sqlite3 / op-sqlite）、文件存储适配器
  sync/             # CRDT 同步、文件同步
  metadata/         # 元数据识别和抓取（DOI、arXiv、Crossref、OpenAlex……）
  ai/               # 模型接口、提示词、RAG
  translate/        # 划词翻译、全文翻译、术语表
  annotation/       # 跨平台批注格式：定义、序列化、导出为标准 PDF 批注
  ui/               # 共享设计规范（颜色、字体、间距等 token）
docs/
```

**规则**：`packages/core` 及其他共享包不能引用 Electron、Node 专属 API 或 React Native 专属 API，平台相关的能力通过适配器注入。

## 4. 同步设计

| 数据 | 方式 | 说明 |
|---|---|---|
| 元数据、标签、文件夹 | CRDT | 字段级合并 |
| 批注（高亮、笔迹） | CRDT | 每条批注是独立对象，大部分是新增，几乎不会冲突 |
| 笔记 | CRDT（文本类型） | 多设备同时编辑也能合并 |
| PDF 文件 | 按内容哈希（SHA-256）存储 | 自动去重；新设备先同步元数据，打开时再拉文件 |
| 向量索引 | **不同步**，各设备本地重建 | 避免同步大体积数据；也可以以后提供可选同步 |

同步后端可以选：
1. 第一版：**文件式同步**。把 CRDT 的变更日志和 PDF 写进用户自选的存储（iCloud Drive、WebDAV、S3、R2），不需要我们运营服务器；
2. 以后：可选的官方托管同步服务，提供实时性更好的体验（收费来源之一）。

## 5. AI 设计

| 层级 | 能力 | 实现要点 |
|---|---|---|
| 划词 | 解释、翻译、追问；用 Pencil 圈选也能触发 | 把选中内容和前后文一起发给模型 |
| 单篇 | 速读卡片、问答 | 把 PDF 解析成带位置信息的段落；回答必须带原文定位 |
| 全库 | 跨论文问答、对比表、相关工作草稿 | 本地向量检索 + 全文检索混合召回（RAG） |

- 结果缓存在本地，同一篇论文不重复计费；
- 显示每次调用的费用和累计费用；
- 发送内容之前明确告知用户；提供本地模型选项。

## 6. 元数据识别流程

1. 从 PDF 里提取 DOI 或 arXiv ID（检查文本、PDF 元数据、文件名）；
2. 用 Crossref、OpenAlex、arXiv 的 API 查询；
3. 查不到时用 GROBID 或大模型从 PDF 首页解析标题和作者，再用标题去搜索匹配；
4. 自动合并预印本和正式发表版本；
5. 自动按规则重命名文件，去重。
