# 11 移动端与同步规划

> 状态：v0.2（2026-11-09）。第 8 节的事已经决定（见第 9 节），S1 桌面同步已经做完，进度记在 [10-桌面MVP实施计划](10-桌面MVP实施计划.md) 的"S1 同步"。依据的是桌面 0.1.4 的代码和 [03-技术架构](03-技术架构.md)、[06-路线图](06-路线图.md)。

## 1. 结论

1. **先做同步，再做移动端。** 对 Flax 来说，没有同步的手机版和 iPad 版只是一个孤立的 PDF 阅读器。同步可以先在两台电脑之间开发和验证，不用等移动端。
2. **移动端用 React Native（Expo），三个平台一套代码。** 文献库、详情、笔记、AI 对话、设置写一次，iPhone、iPad、Android 共用。
3. **阅读器按平台分开做：**
   - **iPhone 和 iPad**：共用一个原生模块，用 Swift 写，基于 PDFKit 和 PencilKit。
   - **Android**：先在 WebView 里跑 PDF.js，复用桌面阅读器的逻辑。
4. **同步不用通用 CRDT 库，改成"按记录、按字段合并"的变更日志。** 日志写到用户自己的存储上，第一个支持的后端是 WebDAV（坚果云、Nextcloud、NAS）。理由见第 4 节。
5. **顺序**：
   1. 同步，桌面端之间。
   2. iPad。
   3. iPhone，iPad 的代码基本都能用，主要是改界面布局。
   4. Android。

## 2. 现在的代码哪些能直接用

| 部分 | 现在在哪 | 移动端能不能用 |
|---|---|---|
| 数据模型、仓储层、元数据识别、引用格式、批注定位、笔记解析、AI 的纯函数 | `packages/core`（约 2400 行，不依赖平台） | **直接用**。`SqlDb` 接口当初就是为了换驱动留的 |
| 导入流程、AI 服务和各家模型接口、机器翻译、笔记仓库 | `apps/desktop/src/main`（用了 `node:fs`、`node:crypto`、Electron） | **逻辑能用，要先搬家**：挪进 `packages/*`，文件、哈希、网络、钥匙串改成注入的适配器 |
| 筛选、标签、阅读状态、笔记链接、实时预览这些纯函数 | `renderer/src/lib`、`components/livePreview.ts`、`slashMenu.ts` | **直接用**，挪到共享包 |
| 界面组件（文献库表格、详情、侧边栏、设置等） | `renderer/src/components`，React DOM | **不能直接用**，要用 React Native 重写。布局本来就要为触屏重新设计，重写是合理的 |
| 笔记编辑器 | CodeMirror 6 | **能用**：用 Expo 的 DOM 组件（`'use dom'`）把它包在 WebView 里 |
| 阅读器 | PDF.js 加自己的批注层（`Reader.tsx` 1100 多行，`geometry.ts`、`overlay.ts`） | iPhone 和 iPad 用原生阅读器替换。Android 版在 WebView 里复用这套代码 |
| macOS 系统翻译 | 随应用带的 Swift 小助手 | iOS 有同样的 Translation 框架，可以写成原生模块 |

**要做的准备工作**：先在桌面端把主进程里平台无关的部分挪进共享包，桌面端行为不变。这一步也让测试更好写。

## 3. 移动端

### 3.1 为什么还是 React Native

| 方案 | 好处 | 问题 |
|---|---|---|
| **React Native（Expo）+ 原生阅读器** ✅ | 共享 TypeScript 核心；界面是真正的原生控件；`fetch` 没有跨域限制，元数据和 AI 请求可以直接发；Pencil 部分完全原生 | 界面要重写 |
| Capacitor 套现在的网页界面 | 复用最多，几乎不用重写界面 | WebView 里用 Pencil 延迟明显（03 已经否决）；iOS WebView 里的文字选择和手势不像原生；网络请求有跨域限制，要绕到原生层 |
| 每个平台原生开发（Swift + Kotlin） | 体验最好 | 三套界面，核心逻辑要么重写要么跑在 JS 引擎里，现在的人手做不下来 |
| Flutter | 一套界面 | 不能复用 TypeScript 核心；PDF 生态弱（03 已经否决） |

**选 Expo 的理由**：
- 不用手动维护 Xcode 和 Gradle 工程，用 prebuild 和 dev client 就能接自己的原生模块。
- `expo-sqlite` 有同步接口，可以实现 `SqlDb`。
- `expo-secure-store` 存 API Key，iOS 上进钥匙串，Android 上进 Keystore。
- `expo/fetch` 支持流式读取，AI 回答可以边生成边显示。
- DOM 组件可以直接复用 CodeMirror。

### 3.2 iPhone 和 iPad 的阅读器（原生模块）

- **渲染和选择**：用 PDFKit 的 `PDFView` 渲染、选择文字和查找。批注不用 PDFKit 自己的 `PDFAnnotation` 存储，而是在页面上叠一个自己的层，按 [04-数据模型](04-数据模型.md) 的格式画高亮和笔迹，跟桌面一样不改 PDF。
- **笔迹**：用 PencilKit 的 `PKCanvasView` 记录，每页一个，跟着页面一起缩放。存的时候转换成开放格式：点序列、压力、时间。
- **笔势**：划过文字自动吸附成高亮，在第二阶段的 iPad 范围里。圈选问 AI 也在这个范围里。
- **坐标**：PDFKit 的页面坐标和桌面一样，都是 pt，原点在左下角。这一点要先验证：同一条高亮在 PDF.js 和 PDFKit 上的位置要一致。路线图阶段 0 里有这一项，**写阅读器之前先做**。
- **和 JS 的接口**：原生阅读器只负责显示和收集输入。批注的增删改都发事件给 JS，由 JS 里的 `Library` 写数据库，保证只有一个地方写数据。
- **iPhone**：用同一个模块，只是默认适合宽度、单页滚动，工具栏收进一个按钮。PencilKit 在 iPhone 上也能用手指写。

### 3.3 Android 的阅读器

- **第一版**：用 WebView 加 PDF.js，复用桌面的渲染、批注层和引用预览代码。手写笔用 Pointer Events，能拿到压力。
- **以后**：如果手写延迟不够好，换成原生实现。可以用 Jetpack 的 PDF 库加 Jetpack Ink，或者 PDFium。这一步等真的有 Android 平板用户再做。

### 3.4 移动端的界面怎么组织

| 设备 | 结构 |
|---|---|
| iPad | 跟桌面接近：侧边栏（文件夹、标签）加论文列表；阅读器全屏；笔记和 AI 可以从右边分屏拉出 |
| iPhone、Android 手机 | 底部标签栏分四项：文献库、笔记、收件箱、设置；阅读器全屏。手机上以**判断要不要读、回顾高亮、问 AI** 为主，不追求跟桌面一样精读 |

手机上最好的阅读体验是 HTML 阅读模式，见 [07-阅读格式与手写策略](07-阅读格式与手写策略.md)。不过 HTML 阅读模式在阶段 3，手机第一版先用 PDF 适合宽度的方式。

### 3.5 移动端第一版不做

- 从 Zotero 或 BibTeX 导入。这类整理工作在桌面上做，同步过来就行。
- 用户自己指定数据目录。
- 术语表编辑。手机和 iPad 只读，在桌面编辑。

### 3.6 要先决定或核实的事

| 事项 | 说明 |
|---|---|
| **Apple 开发者账号（99 美元一年）** | iPhone 和 iPad 版必须有：TestFlight、App Store 都要。现在 Mac 版是自签名，没走苹果公证。有了账号，Mac 版也可以改成 Developer ID 签名加公证，用户打开时不会再被拦。用 iCloud 同步也要这个账号（见 4.6） |
| Android 怎么分发 | Google Play 一次性 25 美元；或者直接在 GitHub 发 APK。国内应用商店需要 APP 备案和软著，**要核实** |
| 中国区 App Store | 新上架的应用需要 ICP 备案号；AI 功能是否需要额外备案，**要核实**。现在的 AI 都是用户自带 Key，可能有区别 |
| AGPL 和 App Store | 版权在自己手里，可以用 App Store 发布。前提是外部贡献者都签了 CLA（[02-开源与许可证](02-开源与许可证.md) 里已经计划了） |

## 4. 同步

### 4.1 要同步什么

| 数据 | 现在存在哪 | 同步方式 |
|---|---|---|
| 论文（元数据、标签、文件夹、阅读状态、评分、论文要点） | `papers` 表，每行一个 JSON | 按字段合并；标签和文件夹按集合合并 |
| 批注 | `annotations` 表 | 每条批注是独立记录，基本只会新增，几乎不会冲突 |
| 文件夹、术语 | `folders`、`terms` 表 | 按字段合并 |
| 标签颜色 | `meta.tagColors`，所有标签一个 JSON | **要先改**：拆成每个标签一条记录，否则两台设备各改一个颜色会互相覆盖 |
| 笔记 | `notes/*.md`，可以用 Obsidian 直接改 | 整篇作为一条记录；冲突时按行做三方合并，合并不了就留一份冲突副本（见 4.4） |
| AI 对话 | `ai/conversations/*.json` | 每条对话一条记录，消息只追加 |
| PDF 文件 | `files/ab/<sha256>.pdf` | 按内容哈希上传；其他设备先只拿元数据，打开时再下载（数据模型里已经有 `localState: remote_only`） |
| 阅读位置 | 论文记录里的 `readingPosition` | 每台设备一份，打开时提示"在 iPad 上读到第 12 页，跳过去？" |
| **不同步** | API Key、外观、数据目录、翻译缓存、以后的向量索引 | 每台设备自己设置或自己重建。Key 跟设备的钥匙串走，不离开设备 |

### 4.2 为什么不用 Automerge 或 Yjs

03 原计划用通用 CRDT 库，现在建议不用，有三个原因：

1. **数据本来就是一条条记录。** 现在的仓储层每行存一个 JSON，删除是软删除，记录都有 `id`、`updatedAt`、`deviceId`。按字段合并就能覆盖论文、批注、文件夹、术语，冲突规则一句话能说清楚。
2. **笔记是普通的 `.md` 文件，用户可以用别的编辑器改。** CRDT 文本要求每次编辑都经过它，外部编辑器一改就只能整篇替换，CRDT 的好处就没了。三方合并对"在两台设备上改了同一篇笔记的不同段落"已经够用。
3. **库和存储成本。** 用通用 CRDT 库，数据要整体换成它的文档格式，历史会越来越大，React Native 上的性能还要测。自己的日志格式简单，可以直接导出、直接查看。

如果以后真的需要"两台设备同时编辑同一篇笔记，实时合并"，可以只对笔记正文引入 Yjs，不影响其他数据。

### 4.3 合并规则

- **时钟**：每台设备用混合逻辑时钟（HLC，物理时间加计数器加设备 ID）给每次修改打时间戳。电脑时间不准也不会把新改动当成旧的。
- **普通字段**：每个字段单独记时间戳，晚的赢。在 iPad 上改了标题、在电脑上改了阅读状态，两个都保留。
- **集合字段**（标签、文件夹）：按"加了哪个、删了哪个"合并，不整体覆盖。一边加了标签 A、另一边加了标签 B，结果两个都有。
- **删除**：继续用现在的软删除，删除标记保留 90 天以后才真正清掉。如果删除之后另一台设备又改了这条记录，按"删除赢"处理，但在设置的同步页面里列出来，可以恢复。
- **论文要点**：已经是逐字段记 `source`，按普通字段合并就行。
- **合并只在 core 里做**：写一个 `merge(local, remote)` 纯函数，所有平台共用，用测试把规则固定下来。

### 4.4 笔记的冲突

1. 每篇笔记记下上次同步时的版本（基础版本）。
2. 两边都改了时，按行做三方合并。改的是不同行，就自动合并。
3. 改了同一行时，本地保留自己的版本，另存一份 `标题（来自 iPad 的冲突版本）.md`，并在笔记列表里标出来。不弹窗、不让用户当场选。

### 4.5 存储格式

同步的后端只需要"列目录、读文件、写文件、删文件"四个操作。WebDAV、S3、本地文件夹都能做到。目录结构如下：

```
Flax/
  library.json                 # 库的 ID、格式版本、是否加密
  devices/<deviceId>.json      # 设备名、最后同步时间、读到了每台设备日志的哪个位置
  log/<deviceId>/<序号>.jsonl.gz   # 这台设备的修改，只追加
  snapshots/<deviceId>-<时间>.json.gz   # 定期合并的快照，新设备从快照开始
  files/ab/<sha256>.pdf        # PDF，和本地的存法一样
```

- **每台设备只写自己的目录。** 两台设备永远不会同时写同一个文件，坚果云、Nextcloud 这类没有锁的存储也安全。
- **拉取**：读其他设备日志里自己还没读过的部分，合并进本地数据库，记下读到的位置。
- **推送**：本地的修改先写进本地的待发送表，攒几秒写成一段日志上传。没网时一直攒着。
- **清理**：所有设备都读过的日志，在下一次生成快照后删掉。一台设备超过 90 天没同步，就不再等它，它回来时从快照重新开始。
- **出问题时**：日志是 JSON 行，可以直接看。快照可以当备份用。

### 4.6 后端

| 后端 | 支持的平台 | 适合谁 | 顺序 |
|---|---|---|---|
| **WebDAV**（坚果云、Nextcloud、群晖等 NAS） | 所有平台 | 国内用户首选坚果云；有 NAS 的用户 | **第一个** |
| 本地文件夹 | 只有桌面 | 已经在用 Dropbox、OneDrive、iCloud 同步盘的用户，在电脑之间同步 | 跟 WebDAV 一起做，几乎不用额外的工作量 |
| S3 兼容存储（Cloudflare R2、AWS S3、阿里云 OSS） | 所有平台 | 愿意自己配存储桶的用户 | 第二个 |
| iCloud | 只有 Apple 设备（Windows 上不可靠） | 只用 Mac、iPad、iPhone 的用户，不用注册任何账号 | 第三个。需要 Apple 开发者账号和 iCloud 权限，Mac 版也要改签名方式 |
| 官方托管同步 | 所有平台 | 不想折腾的用户 | 以后（阶段 4，收费） |

**注意**：不要把数据库直接放进同步盘。现在的数据目录可以让用户换位置，如果用户选的是 iCloud 或 Dropbox 里的文件夹，SQLite 可能会损坏（10 号文档里已经写了这个风险）。同步只上传日志，数据库始终留在本地。设置里选数据目录时，选到同步盘要给出提示。

### 4.7 加密

存储在第三方（坚果云、Cloudflare）手里，日志里有用户的笔记和批注。建议**格式从第一天就支持端到端加密**：每段日志和每个文件用库密钥加密，库密钥用用户设的同步密码派生。加不加密由用户决定，开启同步时问一次。

- 好处：服务商看不到内容。
- 代价：忘了密码，云端的数据就打不开，只能从还有数据的设备重新上传。PDF 加密后，服务商那边也不能去重。

### 4.8 跟设备怎么连上

1. 在第一台设备上打开同步，选后端，填地址和账号，设置要不要加密。
2. 在新设备上填同一个后端，或者扫第一台设备上显示的二维码（里面是后端地址和库 ID，**不含密码**）。
3. 新设备先下载快照和日志，PDF 在打开论文时再下载。在设置里可以选"在 Wi-Fi 下下载所有 PDF"。

## 5. 动手前要先改的数据

这些改动在桌面上就能做，做完对现在的用户也没有影响：

1. 标签颜色从 `meta` 里的一个 JSON 拆成单独的表，每个标签一行。
2. 每张表加一列，记每个字段的 HLC 时间戳（或者在 `data` 里加 `_clock`）。再加一张本地的待发送修改表。
3. 阅读位置改成按设备存。
4. AI 对话从 `ai/conversations` 的文件挪进数据库，或者至少给每条消息加 ID 和时间戳。10 号文档里本来就写着"对话进数据库以便同步"。
5. 笔记仓库记住每篇笔记上次同步的版本，用于三方合并。
6. 数据目录和包名还是 `Paper`。如果要改名，在有同步之前改最省事，因为同步之后，云端的目录名也要跟着迁移。

## 6. 阶段和顺序

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| **S0 准备** | 把主进程里平台无关的逻辑挪进共享包；第 5 节的数据改动；验证 PDF.js 和 PDFKit 的批注坐标一致 | 桌面端行为不变，测试全过；同一条高亮在两个渲染器上位置一致 |
| **S1 同步（桌面）** | 合并规则和测试；日志格式；WebDAV 和本地文件夹后端；同步设置页；PDF 按需下载 | 两台电脑（Mac 和 Windows）离线各自改，再联网，合并结果正确，没有数据丢失；拔网线、中途退出都能恢复 |
| **S2 iPad** | Expo 工程；文献库、详情、笔记、AI；原生 PDFKit + PencilKit 阅读器；高亮、批注、笔迹；同步 | iPad 上画的笔迹在桌面上位置正确；和桌面来回同步一周没有问题 |
| **S3 iPhone** | 手机布局（标签栏、单栏）；阅读器的手机模式 | 能在手机上判断要不要读、回顾高亮、问 AI |
| **S4 Android** | 同一套 RN 界面；WebView + PDF.js 阅读器；Android 打包 | 手机和平板都能用；手写笔能高亮 |
| 以后 | S3 兼容存储、iCloud、官方托管同步；HTML 阅读模式（手机） | |

这和 [06-路线图](06-路线图.md) 一致：iPad 加同步在阶段 2，手机版在阶段 3，Android 在阶段 4。区别是这里把同步放到了最前面单独做。

## 7. 和原方案的差异（需要确认）

| 原方案（03） | 现在的建议 | 理由 |
|---|---|---|
| 用 Automerge 或 Yjs 做 CRDT | 按记录、按字段合并的变更日志；笔记用三方合并 | 见 4.2 |
| iPad 用原生阅读器，Android 以后用 PDFium | iPhone 也用同一个原生阅读器；Android 先用 WebView + PDF.js | 一个模块覆盖两种 Apple 设备；Android 先复用桌面代码，有需要再换原生 |
| 同步后端先做 iCloud Drive、WebDAV、S3、R2 | 先做 WebDAV 和本地文件夹，然后 S3，然后 iCloud | WebDAV 所有平台都能用，国内有坚果云；iCloud 依赖开发者账号，而且 Windows 上不可靠 |
| 包结构拆成 storage、sync、metadata、ai 等多个包 | 先拆出 `sync` 和平台适配器，其他的等真的需要时再拆 | 现在代码量不大，拆太多包是额外负担 |

## 8. 要你决定的事

1. **Apple 开发者账号**：要不要开？不开就做不了 iPhone 和 iPad 版，也用不了 iCloud 同步。
2. **第一个同步后端**：坚果云（WebDAV）可以吗？还是你主要用别的？
3. **端到端加密**：默认开、默认关，还是开启同步时让用户选？
4. **顺序**：iPad 先于手机，可以吗？还是你更想先在手机上用？
5. **改名**：数据目录和包名要不要在做同步之前改成 Flax？

## 9. 决定（2026-11-09）

| 事项 | 决定 | 影响 |
|---|---|---|
| Apple 开发者账号 | 以后再开 | iPhone、iPad 版先只能在模拟器里跑；装到自己手机上可以用 Xcode 的免费签名（7 天过期）。iCloud 后端也先不做 |
| 第一个同步后端 | 坚果云（WebDAV） | 已经做好，同时支持其他 WebDAV 和本地文件夹 |
| 端到端加密 | 默认开启 | 开启同步时默认勾选"加密"，要设同步密码；可以取消 |
| 顺序 | 手机先于 iPad | S2 改成手机版（先 Android，不需要开发者账号；iPhone 在模拟器里开发），S3 是 iPad |
| 改名 | 现在改 | 资料文件夹改到 `Flax/Library`，包名 `@flax/*`，协议 `flax://`，见 10 号文档的"改名" |

### 做的时候和规划不一样的地方
- 同步代码放在 `packages/core/src/sync/`，没有单独拆成一个包：手机版直接引用 core 就行，以后需要再拆。
- 阅读位置先简单处理成"只属于这台设备，不同步"。规划里的"在 iPad 上读到第 12 页，跳过去？"以后再做。
- AI 对话这次没同步，还在文件里。下一步把它挪进数据库再同步。
- 存储格式：`flax.json`、`log/<设备>/<序号>.flx`、`snap/<设备>-<序号>.flx`、`devices/<设备>.flx`、`files/<前两位>/<哈希>`。快照写在一个目录里，一次列目录就能看到所有设备的快照序号，省请求。
